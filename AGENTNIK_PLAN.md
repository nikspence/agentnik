# Agentnik implementation plan

Reviewed after the v0.2.0 release: 2026-11-08. This roadmap describes the current development tree and the remaining acceptance gates. Detailed historical evidence is in [VALIDATION.md](VALIDATION.md); installation and delivered behavior are in [README.md](README.md).

## Objective and preserved contracts

Agentnik is an independent Python/Qt desktop application for chat, Ollama System One decisions, bounded web research, and a repository-based Coding Agent workspace. Keep runtime dependencies small and support Windows, macOS, and Linux without claiming untested platform compatibility. Plan a localized interface without changing the language of user or model content.

- Preserve the robot geometry, red robot/`nik` branding, theme-sensitive `agent` wordmark, independent application identity/storage, and Apache License 2.0 with **Copyright 2026 Nikolaus Spence**.
- Preserve independent tabs and histories, responsive background work, Markdown, inline thinking, images, statistics, accessibility, themes, saved prompts, and attachment cleanup.
- Preserve Responses, Chat Completions, Messages, and native Ollama chat. Bedrock support remains Mantle bearer-token endpoints. A protocol name does not establish model capability.
- Keep System One separate from chat/research: ordered questions and criteria, multiple images, and image-only state fallback remain supported.
- Keep secrets in the credential store or the existing explicit plaintext fallback. Exclude credentials from history, logs, tool records, screenshots, and exports by default. Preserve confirmation for destructive history actions.
- Ordinary tests remain offline. No background inference probes, paid requests, or live research requests during routine validation. Live checks require an authorized, explicit endpoint/model/route selection.

Chat research limits can be adjusted per chat. These are separate limits, not a guarantee that total retained session storage is 64 KB.

## 3. Lessons retained from implementation

- **Readiness needs application evidence.** The first frozen check was too impatient. Wait for a process-owned Qt window and temporary database within a deadline, then request a graceful close and verify exit status. Input-idle alone is insufficient; startup success is narrower than interactive success.
- **Protocol compatibility is narrower than capability.** Keep separate adapters, structured tool histories, opaque reasoning, identifiers, completion reasons, and missing-usage states. Do not infer hosted support from a Responses-shaped gateway.
- **Fallback can duplicate remote work.** Retry only eligible explicit outcomes within budgets. Stop on cancellation, access restriction, partial output/tool activity, or uncertain execution. Do not change model/provider or use alternate routes to bypass restrictions. Empty results are research evidence, not a transport failure.
- **Cancellation is cooperative.** Stop scheduling and reject late results immediately; remote computation/billing and outstanding local socket operations may continue until their own bounds. Test resource behavior across repeated cancellations, not just one late result.
- **External navigation needs honest disclosure.** Direct fetch has local controls; search services and hosted tools do not inherit those controls. Do not silently weaken strict policy or enable service-backed fetch.
- **Discovery should identify destinations without erasing user intent.** Environment-discovered `0.0.0.0` means connect to `127.0.0.1`. Merge matching environment/probe discoveries, retaining environment metadata and useful probe information. Preserve independently saved connections and avoid treating arbitrary DNS names or IPv6 destinations as equivalent.
- **Small asset defects affect runtime quality.** Empty SVG paths caused Qt warnings. Retain parser-warning coverage and inspect both themes. Editing/resending a historical prompt restores a draft and appends a new turn on Send; it does not rewrite history.
- **Build and release are distinct.** A wheel, source test suite, local frozen startup, and portable desktop release establish different evidence. The first release archive included documentation/license through manual assembly; automate that step before repeating releases.

### Additional lessons from v0.2.0

- Discovery is availability advertising, not account entitlement: explicit upstream rejections explain why some listed models cannot be tested. Capability evidence needs endpoint, protocol, alias and credential context; opaque scopes prevent one account's result from becoming another account's claim.
- Real service behavior can differ from headers. Ollama returned valid JSON labeled as HTML; the compatibility exception is confined to its fixed search POST and still requires valid JSON/results. Do not generalize this into permissive content sniffing.
- Partial evidence and executable continuation serve different purposes. Preserve interrupted work for inspection, but never replay incomplete tool exchanges. Size limits cover retained metadata separately from wire/model context, and reduction must be visible.
- Cancellation bounds client scheduling, not remote computation. Retain worker admission slots until workers actually exit; nested waits need nonblocking capacity handling to avoid deadlock. A global research limit does not also cap ordinary chat/discovery jobs.
- Release validation must exercise the entire assembly path. v0.2.0 exposed variable shadowing after image copying that broke manifest serialization despite successful freezing/startup. The new assembly regression covers source metadata, images and archive creation together.
- Keep startup checks independent of shell execution policy. The Python Windows helper checks the actual process-owned Qt window and database under a deadline, without changing PowerShell policy. Wait for readiness; input-idle alone is inadequate.
- Artifact provenance matters: build clean committed sources, check the final manifest matches the intended tag/version, verify ZIP/checksum, then tag/push. A local archive, pushed tag and uploaded GitHub Release are separate deliverables. Do not retrofit or overwrite older release artifacts.
- Favor small modules and explicit storage contracts as the UI grows. The new session, retention and research-settings modules isolate policy from presentation; continue that separation for repository management and code panes.

### D0.2 Usage and durable state

`core.usage_metrics` normalizes primary input/output counts but does not yet model cache-related provider detail. Define per-request usage snapshots and preserve bounded, sanitized provider details where useful. Messages `message_delta` usage is cumulative: update the request snapshot rather than summing deltas. Define cache read/write semantics before aggregating; missing values stay unknown, failed-attempt usage remains included, and no cost is invented. The [Messages streaming contract](https://platform.claude.com/docs/en/build-with-claude/streaming) documents event ordering and cumulative usage.

Validate saved connection/backend settings and versioned session shapes before use. Specify recovery for corrupt/truncated configuration, safe defaults for old sessions, and rejection of unsupported future versions without destroying the original file. Retain atomic configuration writes and shared attachment cleanup. Review capability invalidation when connection credentials/configuration change; verification evidence needs scope, date, and method.

Set an explicit total retained research-record limit covering sources, activity, partial exchanges, annotations, and metadata, separately from model-context limits. Test large failures and interrupted reopen. Reopening history must never restart tools or requests.

Acceptance: cumulative/cache/missing usage fixtures reconcile without double-counting; malformed settings produce recoverable errors; bounded persistence survives save/reopen and excludes credentials.

D0.2 progress: sanitized per-request usage snapshots now preserve cache and reasoning counters, update cumulative deltas without summing them, and aggregate once across model requests/route attempts. Messages total input includes its separately reported uncached/cache-read/cache-write tokens; detail counters already included in other protocol totals are not added again. Saved configuration loading now validates supported versions, connection/settings/backend shapes and duplicate backend IDs before opening the history database. Invalid files are preserved and produce an actionable repair/restart message; legacy valid configuration and credential references remain compatible. The offline suite has 106 passing tests. Versioned session validation/recovery and retained-record limits are now implemented: unreadable/future records remain visible without rewriting their stored payload, valid legacy records gain in-memory defaults, uncertain attachment references prevent cleanup, and new research snapshots have a separate 256 KB metadata budget with visible truncation and disabled incomplete continuation. The offline suite now has 115 passing tests, including offscreen interrupted reopen without requests. Nested research defaults/capabilities are now validated, and opaque credential-context scopes prevent accounts on one endpoint from sharing verification. Saved connection changes invalidate prior evidence; observed environment changes rotate in-memory scopes, and late completions cannot re-verify a changed request context. Legacy explicit enablement can carry forward, while unbound verification requires a fresh scoped check. The 122-test offline suite covers these behaviors. D0.2 local hardening is complete; next is D0.3 worker/transport/Qt lifecycle validation. No live compatibility evidence was added by this slice.

### D0.3 Worker, transport, and Qt lifecycle

Test rapid cancel/restart and simultaneous tabs with stalled DNS, web, and model workers. Add an aggregate concurrency/resource bound if existing per-turn deadlines allow abandoned workers to accumulate; reject late results without compromising responsiveness. Keep remote-stop limitations explicit.

The pinned transport now attempts up to eight distinct approved addresses for TCP connection establishment under one deadline and the original TLS hostname. No second DNS lookup is performed. TLS failures are terminal; HTTP submissions are not replayed for address failover. Retain redirect, content-type, compression, and byte restrictions. Richer extraction/charset support is optional follow-up, not a reason to relax transport controls.

Check that research completion preserves the user's thinking expansion choice just as ordinary chat does. Exercise cancellation, draft retention, edit/resend, source links, independent tabs, interrupted reopen, and light/dark presentation. Expand discovery regressions for saved-profile independence and environment/probe precedence.

TCP failover is bounded to approved addresses and stops on TLS errors. Research completion retains thinking visibility across save/reopen. The 131-test offline suite covers repeated cancellation/restart, nested waits/timeouts, two-tab isolation and late results, both themes, saved-profile/discovery precedence, plus existing strict-policy, citation, prompt, and interrupted-history checks. ### Optional System One command safety recommendation

Implemented preview: an opt-in Code-pane setting checks shell proposals with the selected Decision connection/model. The request contains the exact command, working directory, shell and inherited environment variable names, not environment values or file contents. The UI shows the decision endpoint and an advisory category and confidence, or UNKNOWN on invalid/failing/timeout results; manual approval remains required. The request has a 15-second bound and stale or cancelled results are ignored. The category descriptions are fixed guidance, not model-generated reasons. Offline fixtures cover the request and approval lifecycle; real-model compatibility remains unverified.

When the Coding Agent is ready to request approval for a proposed command, optionally run a configured System One decision model against that command and a deliberately limited context (for example, working-directory scope and the intended operation). Show the result alongside the exact command in the approval view as a concise recommendation with reason text and one or more clear badges. Suggested categories include **Safe**, **Risky**, **Privacy**, **Warning**, and **Danger**; define the structured decision schema and mapping so labels are consistent and explainable. Multiple badges may apply, and an uncertain or incomplete result must be shown as **Unknown** or **Review needed**, not silently treated as safe.

This check is opt-in and advisory. It never grants approval, suppresses the normal user approval step, or replaces enforced execution boundaries. The user sees what command and context will be sent, which configured decision endpoint/model will receive it, and the result before approving or rejecting. If the check is disabled, unavailable, times out, or returns invalid output, present that status plainly and continue only through the ordinary approval policy; do not represent missing review as a safety pass. Do not send secrets or unrelated conversation history. Preserve the recommendation and its scope in the session's bounded audit record without storing credentials.

## 9. F — MCP servers and Skills (long term)

Support chat and coding where appropriate, with capabilities explicitly enabled for each session/project. ### F1: MCP server configuration and connections

First preview: the MCP servers manager saves and removes local stdio commands, enables/disables them, and runs an explicitly confirmed, time- and output-bounded initialization probe using protocol 2025-11-25. It displays reported identity and capabilities without exposing tools to models. Commands and arguments are plaintext settings, so credentials must not be placed there. The probe closes the process after the initial response; it does not establish an operational MCP session. That initial local probe does not establish an operational session. Windows validation uses an offline fake server; other platforms are unqualified.

First target for remote support: Parallel MCP at https://mcp.parallel.ai/mcp. An explicitly authorized Windows live probe completed an authenticated 2025-11-25 initialization, received an SSE response and session ID, sent initialized, and listed seven tools. No MCP tools were invoked. Agentnik's existing Parallel Search API adapter separately returned three search results with the supplied credential. Those direct probes preceded Agentnik's remote transport; see the implementation evidence below. Never store the key in server arguments or project files.

Remote discovery preview now supports HTTPS with optional keyring-backed bearer tokens, JSON or SSE responses, initialization, session headers, initialized notification and bounded tools/list pagination (five pages or 100 names). The manager displays bounded, explicitly untrusted tool descriptions and input schemas, marking missing or oversized metadata. Completed probes attempt to close sessions and report when closure is not confirmed. No tool calls are exposed to models; OAuth, stream resumption, server-initiated requests, and persistent sessions remain future work. Agentnik's Qt transport completed a live authenticated Parallel discovery on Windows and listed seven tools and their input schemas without invoking them. Offline fake-server tests cover the handshake and credential handling. Other servers and platforms remain unqualified.

The manager also supports explicitly reviewed, one-shot remote tool calls. The user supplies a JSON object and sees the destination, tool description, schema and complete arguments before approval. Agentnik rediscovers the tool in a fresh session and refuses a changed or incomplete definition, sends one call, reports uncertain outcomes without retry, and displays bounded untrusted results. Arguments are validated in a background worker against a conservative JSON Schema 2020-12 subset; unsupported keywords and remote references are rejected without network retrieval. Model-initiated remote calls are available in the Code preview. A Windows live Parallel `web_search` returned a result and closed the session, and its actual schema accepted valid arguments and rejected a missing required field; offline tests cover success, changed metadata, uncertain response and approval denial. Other platforms and servers remain unqualified.

Local stdio sessions now complete initialization and bounded tool discovery, remain open across explicitly reviewed calls, and close when the server selection or manager closes. Windows npm npx shims use the installed Node npm CLI. Local negotiation accepts supported 2024-11-05 through 2025-11-25 versions. Nullable anyOf variants are accepted by the bounded schema validator. Windows live validation of microsoft/postgres-mcp 0.3.0 discovered tools and a saved profile, and later connected to mcptest after the profile password was corrected. A temporary table was created, written, read and dropped. The role lacked CREATE permission on the public schema for permanent tables. Offline tests cover persistent calls and UI approval. Other platforms remain unqualified.

Code can opt into one enabled local stdio server for a run. The model may request discovery and calls through generic tools; startup and every call require separate review, arguments are validated against the supported schema subset, the process remains available for stateful calls, and output is untrusted and sent to the model. Configuration changes prevent further requests; cancellation closes the session. Offline tests use mocked model calls and a fake stdio server; live model-driven MCP workflows remain unqualified. A selected remote HTTPS server can also be used by Code with reviewed discovery and each call. Coding runs keep a single HTTP session when the server supplies a session ID, check tool metadata again before each call, and attempt session termination on completion or cancellation. Manual remote calls remain one-shot. Stream resumption and unsolicited notifications are not supported. Windows live Parallel discovery and two web_search calls succeeded in one session through the coding bridge, followed by a shutdown request; model responses were not involved. A fake stateful server verified session reuse, unique request IDs, stale-tool rejection and DELETE. An uncertain call blocks later remote calls in that run.

Remote Streamable HTTP negotiation accepts server-selected versions 2025-03-26, 2025-06-18, and 2025-11-25, and uses that version in subsequent request and session-termination headers. Unsupported versions are rejected before initialization completes. Offline HTTP fixtures test both older versions and session reuse; live compatibility with older remote servers remains unqualified.

Streamable HTTP SSE response parsing supports LF, CRLF and CR line endings, UTF-8 BOMs, empty priming events and multiline data. It rejects unfinished data events, including an otherwise valid response lacking its event terminator. Offline HTTP fixtures cover CR-only responses and an incomplete tool response with an uncertain outcome; stream resumption is not implemented.

Local and remote MCP protocol errors now expose a bounded, sanitized, explicitly untrusted server message and code, without error data. A protocol error during a tool call is treated as uncertain because server-side effects may have occurred; the session stops rather than replaying the call. Offline stdio and HTTP fixtures cover diagnostics and uncertainty.

MCP input schemas may explicitly declare JSON Schema Draft 7; they are checked with Draft 7 semantics, including its handling of `$ref` siblings. Undeclared schemas continue to use 2020-12. Both dialects retain the same bounded keyword and local-reference policy. Offline tests cover accepted, rejected, mixed-dialect and cyclic schemas; live compatibility remains unqualified.

MCP argument validation accepts acyclic references to root `$defs` and legacy `definitions` and bounded `anyOf`, `oneOf`, and `allOf` combinations, supporting common generated tool schemas. External references, recursive references, nested definition scopes, regular expressions, and excessive complexity remain unsupported; the validator never retrieves schemas from the network. Offline tests exercise valid and invalid arguments and reject recursive and external references.

Local stdio tool calls now re-list tool metadata in the same session before execution and stop if the reviewed definition changes, including a change to task execution requirements. Required task-based execution is explicitly unsupported and blocked for local and remote tools. Windows live postgres-mcp profile discovery, mcptest connection and a read-only query passed with local tool rechecks; a fake server tested silent metadata changes.

Code can list up to five pages or 100 resources, with a 200 KB metadata budget, from a selected local stdio server, then read text from an exact listed URI. Listing and each read need individual approval before metadata or text is sent to the model. Reads reject binary contents, mismatched URIs, oversized output, and unsolicited list changes. Remote HTTPS resources use the same reviewed listing and text-read workflow in the existing session. Resource listings report when pagination or size limits leave more resources. Fake local and authenticated HTTP servers test resource reads; a Windows live Parallel resource listing succeeded but returned no resources, so no live resource read was possible.

Code can list and retrieve text-only MCP prompts over local stdio or remote HTTPS, with separate approval for listing and each retrieval. Listings are bounded to five pages, 100 prompts and 200 KB; retrieval accepts only declared string arguments, rechecks the definition, and returns messages as untrusted tool output rather than privileged chat messages. Non-text prompt content is unsupported. Offline local and authenticated HTTP fixtures cover discovery, retrieval, changes, validation, and credential isolation. Live Parallel advertised prompts but returned an empty list; live retrieval remains unqualified.

Code can list resource templates in local or remote sessions, with a bounded five-page/100-item listing and separate approval for listing and each read. Simple scalar `{name}` URI expressions are expanded with percent encoding; unsupported URI-template expressions are marked unavailable. The exact template, variables, and expanded URI appear in approval and the response must match that URI. Fake local and authenticated HTTP servers cover template expansion and reads; a live Parallel listing returned no templates, so live reads remain unqualified.

Resource template expansion also supports scalar multi-variable simple, path (`/`), query (`?`), and query continuation (`&`) expressions. Values are percent-encoded, and omitted or null variables are undefined; reserved expansion, modifiers and composite values remain unsupported. Offline tests cover expansion and validation; live servers using these expressions remain unqualified.

Code can select up to five enabled local or remote MCP servers per run. Multiple-server model requests specify the exact selected server name; discovery metadata, resource and prompt lists, sessions and cancellation remain isolated per server. Each connection and operation is reviewed separately. Single-server model tool shapes remain compatible. Offline tests cover colliding tool names, unselected servers, exact routing and session cleanup. On Windows, separate Parallel and postgres-mcp sessions remained open together while a live Parallel search and read-only mcptest query succeeded; this did not use a live model.

Tool discovery and call reviews display bounded server-supplied annotation hints as untrusted metadata. Hints never change approval decisions, and changes to supported hints invalidate the reviewed tool definition. Offline tests cover metadata validation and the coding approval path.

MCP operation reviews offer an explicit per-server, per-run allow choice alongside one-operation approval and rejection. The allow choice covers subsequent MCP operations on that server, including writes and data access, but not other servers or shell commands; it is cleared on cancellation or completion and is never persisted. Schema, credential, configuration, metadata, resource, and budget checks remain in force. Auto-allowed operations are recorded in coding activity. Offline tests cover scope isolation, invalid/stale decisions, expiration and argument validation.

Local stdio servers can optionally map target environment variable names to existing Agentnik process environment variable names. Settings store only names and preserve legacy configurations; startup review shows the mapping names. Values are captured when the coding run is created or manual test starts, are treated as sensitive, and reflected values are blocked from MCP responses. Missing values prevent startup. Local servers continue to inherit the application environment. Offline tests cover persistence, subprocess mapping, missing variables, model isolation, and reflected-secret blocking.

Local stdio sessions respond to server-initiated `ping` requests and return method-not-found for unsupported server requests, with a bounded request rate and no change to user approval or model permissions. Offline fake-server tests cover pings interleaved with initialization, discovery and calls, unsupported requests, ID collisions and flooding. Server-initiated HTTP requests remain unsupported.

Windows local stdio MCP processes are assigned to a kill-on-close job before initialization is sent, and the job is closed on session shutdown, cancellation, startup errors, and server exit. A Windows subprocess fixture verified termination of a child created after assignment; isolation failure prevents the initialization request. Postgres-mcp startup was live-checked. Assignment occurs after process creation, so already-spawned or breakaway children may escape; non-Windows descendants remain unqualified.

- Provide a server manager to add, edit, enable/disable, remove, and test configured servers. Plan for local process-based and remote HTTP connections; select supported transports, protocol versions, and authentication flows against the official MCP specification during implementation.
- Show server identity, connection status, discovered capabilities, and the permissions/data exposure involved. Store credentials through the existing credential mechanism and exclude them from exports. Review local launch commands and remote destinations before connecting; discovery of a server is not authorization to launch or use it.

- Run connections off the GUI thread with bounded requests/output, cancellation, reconnect behavior, and local child-process cleanup. Reopening a session does not replay tool calls or silently launch a server.

### Storage, permissions and interoperability

- Design a small, documented versioned Markdown/JSON format in an explicit project-local directory such as `agentnik-plans/`, with separate project context and per-track spec, plan, and metadata. Re-read and detect external edits before writing; a multi-file update must show partial completion if interrupted and must not pretend to be an atomic filesystem transaction. Keep user changes and report conflicts for review.
- Scope context loading to the selected project and selected track, follow existing guidance precedence, sanitize credentials, treat imported content as untrusted, and honor the shared context, request, time and tool budgets. Support cancellation and interruptions without replaying uncertain work. Large or unsupported documents should produce an explicit limit or read-only view, not be silently truncated or normalized.
- Later, implement a **read-only Conductor adapter first**: detect an existing `conductor/` index and tracks, display the upstream files and track provenance, and permit explicit selection without modifying them. Verify the exact index links, task markers, metadata and format against fixtures from a pinned upstream release; do not assume every Conductor version has the same layout. Plan optional import/export or bidirectional updates only after round-trip tests prove unknown Markdown, custom fields, statuses and external edits survive. Preserve the original files; require explicit user choice for any conversion or write. Never treat an imported spec or plugin instruction as permission to run a command or auto-commit.

## Structured Git tools — local preview

Agentnik uses Dulwich for local Git operations without shell commands. The coding agent can inspect tracked status, working-file diffs against HEAD, staged diffs against HEAD, recent history, and local branches. Status checks at most 128 tracked paths and does not enumerate untracked files; use project listing for those.

Every mutation has its own approval:

- `git_stage`: stage explicitly named UTF-8 files or tracked deletions; review the index-to-working-file diff. Ignored untracked files and sensitive/excluded project paths are rejected.
- `git_unstage`: restore selected index entries to HEAD without changing working files or other staged entries.
- `git_commit`: commit explicitly named working files from a clean index.
- `git_commit_staged`: commit the reviewed index snapshot; the explicit paths must name every staged change, so unrelated staged entries cannot slip in. Later working-file edits remain untouched.
- `git_create_branch`: create a local branch at the reviewed HEAD without switching branches or overwriting an existing branch.

Path lists are JSON arrays encoded as strings, limited to 32 files. Diffs and UTF-8 file reads are bounded. Commit approvals show the full diff, message, configured identity, and parent commit. Approvals bind to the branch reference, HEAD, index fingerprint, and applicable file snapshots; changed state requires a fresh proposal. Index writes are locked, and reference publication uses compare-and-swap. A rare failure publishing the index after a successful commit reports the commit hash and stops the coding run for inspection rather than repeating the commit.

This preview requires an existing HEAD and a registered repository root with a local `.git` directory. Unborn repositories, linked worktrees, in-progress merges/rebases/cherry-picks, hooks, signing, content filters/LFS, and remote operations are outside the supported slice. Files are staged as raw UTF-8 bytes; no attributes-based transformations or external programs run. External filesystem writers are not an OS-level transaction; avoid concurrent repository writes during execution. Korean approval framing is included; model-facing tool descriptions and activity remain English.

Next: credential-safe remote inspection, then fetch and push with explicit destination/branch/commit previews and transport qualification. Branch switching, merge/rebase, signing, submodules, worktrees, and LFS need separate design and compatibility checks. Current evidence is offline temporary-repository tests, mocked coding-loop approvals, and offscreen Qt checks; live-model Git execution and native visual review remain unverified.
