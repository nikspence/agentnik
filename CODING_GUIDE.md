# Coding with Agentnik

Agentnik's Code pane uses your configured model connections to inspect and change files in a selected local project. Coding compatibility has offline test coverage but has not yet been established with live models.

## Start a task

1. Configure a connection in **Connections**. Choose an endpoint and model that support tool calling; an alias appearing in a model list does not establish compatibility.
2. Click **＋ Code**, choose **Add folder** if needed, select the project, and open it. A Git repository is optional. Opening a pane does not start inference.
3. Select the **Heavy model** connection and enter its model alias, or use **Choose model…**. Optionally configure a separate **Light model** in the same way. You can use different connections and providers.
4. Describe the task and select **Run coding task**. Project file changes apply without per-file approval and appear in activity. Review and approve or reject shell commands and other operations when prompted. Activity follows the bottom until you scroll up; return to the bottom to resume following. Each session retains up to 10,000 activity entries and 4 million text characters, trimming the oldest entries when needed. Long histories use a newer saved-session version; earlier Agentnik versions preserve these sessions as unavailable rather than rewriting them.

The Heavy model plans, reads project files, and makes changes. It may delegate bounded analysis to the configured Light model, which has no repository tools. Project contents read by Heavy can be sent to its endpoint, and delegated context can be sent to the Light endpoint. Choose services appropriate for the contents of your project.

Turn off **Allow Light model delegation** to run with Heavy alone while keeping the Light assignment for later. The setting is saved per Code pane and cannot be changed during a run.

For a practice run, **Try simulated workflow (no execution)** exercises the approval interface without inference or file changes. Simulation approval does not authorize a real edit.

## Review and limits

Project file edits, individual file deletions, and directory creation, rename, and move proceed without per-file approval. The activity view identifies changes and includes a bounded diff excerpt for content edits. Existing files must first be read by the coding agent before content editing; Agentnik checks for changes since that read and again before applying the edit. Deletions support regular files of any size or encoding without reading their contents, and check the source metadata before deletion. If another change conflicts, the operation stops. Shell commands and structured Git mutations still require approval.

When a task changes several files, a conflicting edit does not undo earlier changes. After a conflict, the agent must explicitly read the current file before attempting another edit. Cancellation does not undo changes already applied.

The current tools list directories, read or search UTF-8 files, search within a project directory, write complete file content, delete a regular file, and create, rename, or move directories with existing parents. Search does not replace a file read before editing. The original project search checks at most 500 directory entries, eight directory levels and 512 KB of file data, returning at most 40 matches within 8 KB. It flags incomplete results when limits or inaccessible files prevent a complete search. Full reads and writes are limited to 128 KB per file. Filesystem tools reject traversal, links, and several common credential paths, but these checks are not an operating system sandbox or a guarantee against all external filesystem races.

`rename_file(path, name)` renames a regular file in the same directory. `move_file(path, destination)` moves it to a full project-relative destination path. Binary and large files are supported without reading their contents into the model; no fixed file-size limit is imposed, though run time and available disk space still apply. Destination directories must exist, and existing files are never overwritten. Both paths use the same protected-path, link and guidance checks as edits. Agentnik snapshots the source's identity, size, timestamps and mode to detect changes; this is not an operating-system transaction and cannot detect every possible concurrent modification.

`rename_directory(path, name)` and `move_directory(path, destination)` move a project subdirectory and its contents without overwriting. The destination parent must exist and be on the same filesystem. Agentnik checks up to 10,000 entries, rejects protected paths, links, hardlinked files and nested mounts, and loads nested `AGENTS.md` guidance before proceeding. It requires operating-system support for an atomic no-overwrite directory rename; unsupported filesystems and cross-filesystem directory moves are rejected.

When a hard link cannot be used, the file is copied in bounded chunks to a staging file on the destination filesystem, checked and published before the source is removed. Filesystems without hard links can use an exclusive-create copy; on non-Windows systems that fallback can briefly expose an in-progress destination. Cross-filesystem copies retain file mode and modification time where supported, but may not preserve all ACLs, ownership, extended attributes, or filesystem-specific metadata. If a destination is created but the source cannot be safely removed, the run stops and reports that both paths must be inspected. Renames and moves proceed without per-file approval.

The agent can also propose a shell command. Review the entire command, shell, working directory, environment variable names, and scope before approving. Commands run under your account with network access and access outside the project; they can run Git or other programs and change files without separate file approvals. Agentnik uses PowerShell on Windows and `/bin/sh` on macOS/Linux, passes a limited basic system environment, captures at most 32,000 output bytes, and limits each command to 45 seconds or the remaining run time, whichever is less. Windows uses a process job to stop descendants; POSIX uses a process group, which cannot contain processes that detach themselves. Cancellation cannot undo completed effects. Shell output can be sent to the selected model; known connection keys are redacted, but arbitrary secrets cannot be guaranteed to be detected. Shell execution has Windows build-host smoke coverage and offline approval tests; macOS/Linux native execution and live-model use remain unverified.

For optional shell safety advice, open **Models**, choose a Decision connection and System One model, and enable **Check shell approvals with Decision model** before starting a run. Each proposed shell command sends its exact command, working directory, shell, and inherited environment variable names to that endpoint; it does not send environment values or file contents. These details may still be sensitive. The approval view identifies the endpoint and shows the returned category and any confidence; the category guide is fixed explanatory text, not a model-generated reason. You still approve or reject. A failed, malformed, or timed-out check shows **UNKNOWN** and permits ordinary manual review. File and directory proposals are not checked. Cancellation stops accepting the result but may not stop remote computation. System One compatibility has not been verified live for this feature.

Enable **Allow web research** to let Heavy read public pages without a search key. Agentnik returns page text and bounded same-host links, marked as not yet fetched. **Search settings…** manages ordered search profiles shared with Chat. Choose Brave Search, LangSearch, Firecrawl, Exa, or Parallel and enter its separate API key; these providers work with local inference, LiteLLM, and other tool-capable model connections. Environment alternatives are `BRAVE_SEARCH_API_KEY`, `LANGSEARCH_API_KEY`, `FIRECRAWL_API_KEY`, `EXA_API_KEY`, and `PARALLEL_API_KEY`. Profiles use the OS credential store or explicit plaintext fallback, with at most five saved/environment profiles participating. LangSearch and Firecrawl use search snippets without requesting full-text expansion or scraping. Exa uses auto search plus highlights, and Parallel uses basic search with bounded excerpts; provider search/content charges may apply.

Direct `https://ollama.com` coding connections may also use Ollama search profiles. Other coding connections exclude Ollama search credentials. Configured profiles run first, then Firecrawl Keyless, then legacy Google HTML search after eligible definite rejections. Without a configured provider, Firecrawl Keyless is the default. Select Firecrawl (keyless) explicitly to place it earlier in your saved order; its API key field is disabled. All fallback is recorded; access restrictions, timeout/cancellation, malformed replies, and uncertain outcomes stop it. Google can still be rate-limited or challenged. A Google challenge disables Google for that run while direct public page reads remain available. See [SEARCH_PROVIDERS.md](SEARCH_PROVIDERS.md).

Research is off by default and saved per pane. Page reads go directly to public websites. The Heavy connection's strict public-only navigation policy permits public page reads but disables search, because Agentnik cannot enforce that policy inside an external search service. Searches, page reads, and source IDs and URLs appear in Code activity. Use **Sources** to open or copy links for up to 32 sources from the most recent coding run; the list remains available when the pane is reopened and is cleared when another coding run starts. Search results and discovered links are labeled when their pages have not been fetched. Source IDs apply to that run; check the source material when evaluating the model's conclusions. Web content is untrusted; project file changes can proceed without individual approval. Web calls share the coding run's limits; Light does not get web tools. Authorized live adapter checks returned results and snippets for Brave, Firecrawl Keyless, and LangSearch. A site-restricted LangSearch query returned official Qt documentation after a broader query returned casino-related pages. Provider/model coding integration has offline coverage; live coding research, keyed Firecrawl, Exa/Parallel, and Google scraping remain unverified.

Each run has shared request, tool, context, and time limits. Cancellation stops further scheduling and invalidates pending approval; edits already applied remain in the project. Remote inference may continue or incur charges after cancellation. The pane shows the last completed task and answer, each limited to 2,048 characters. Select **Send previous task and answer with next run** to include that displayed text in a follow-up request to the currently selected Heavy endpoint. The option resets after a successful run. Failed, canceled, and simulated runs do not replace this context. Provider-specific tool exchanges and reasoning are not replayed, and existing files still require a fresh read before editing.

Use **Limits…** beside the delegation and web controls to adjust tool rounds, model requests, tool calls, elapsed seconds, and retained context bytes for the Code pane. Defaults are 8 rounds, 9 requests, 16 calls, 900 seconds overall, and 1,000,000 context bytes, with a 300-second limit per model call. Existing saved limits are preserved; use Restore Defaults to adopt the new context default. The context budget counts previous-task context, assistant continuation, and tool results; it is not the model's total context window and does not include the initial task. Requests from Heavy and Light and calls to project and web tools share the same run budgets. Changes apply to the next run; **Restore Defaults** resets the dialog. The time limit includes time spent reviewing an approval.

Completed and failed runs show reported input and output token totals separately for Heavy and Light. Counts marked **known usage only** omit requests whose provider did not report that count; **unknown** means none of the role's requests reported it. These are reported tokens, not cost estimates. Cancelled runs may not have a final usage summary.

## Projects and history

The **Repositories** manager can rename entries, locate a moved folder, or remove an entry from the list. Removing an entry leaves its files and history intact. Each Code pane keeps a snapshot of its original working directory. After relocating an entry, open a new Code pane to use the new location; an existing pane keeps its original path.

Drafts, model assignments, and bounded activity are saved with the session. Reopening an interrupted run does not resume it or apply a pending edit. Connection credentials are managed through the existing connection settings rather than stored in role assignments.

## Troubleshooting

- If model listing fails, enter the alias manually. Listing success alone does not confirm tool support.
- If the run reports a model or protocol error, check the connection, selected alias, account access, and tool-calling support. Agentnik does not automatically switch models or providers.
- If a project is unavailable, use **Locate folder** in the repository manager and open a new pane. Check the working directory shown in the pane before running.
- If an edit conflicts, inspect the current file and have the agent read the current content before trying again. Earlier changes are not rolled back.

For implementation boundaries and upcoming work, see [CODING_BACKEND_PLAN.md](CODING_BACKEND_PLAN.md). For setup, connection settings, and the rest of the application, see [README.md](README.md).


## Structured Git tools — local preview

Agentnik uses Dulwich for local Git operations without shell commands. The coding agent can inspect tracked status, working-file diffs against HEAD, staged diffs against HEAD, recent history, and local branches. Status checks at most 128 tracked paths and does not enumerate untracked files; use project listing for those.

Every mutation has its own approval:

- `git_stage`: stage explicitly named UTF-8 files or tracked deletions; review the index-to-working-file diff. Ignored untracked files and sensitive/excluded project paths are rejected.
- `git_unstage`: restore selected index entries to HEAD without changing working files or other staged entries.
- `git_commit`: commit explicitly named working files from a clean index.
- `git_commit_staged`: commit the reviewed index snapshot; the explicit paths must name every staged change, so unrelated staged entries cannot slip in. Later working-file edits remain untouched.
- `git_create_branch`: create a local branch at the reviewed HEAD without switching branches or overwriting an existing branch.

Path lists are JSON arrays encoded as strings, limited to 32 files. Diffs and UTF-8 file reads are bounded. Commit approvals show the full diff, message, configured identity, and parent commit. Approvals bind to the branch reference, HEAD, index fingerprint, and applicable file snapshots; changed state requires a fresh proposal. Index writes are locked, and reference publication uses compare-and-swap. A rare failure publishing the index after a successful commit reports the commit hash and stops the coding run for inspection rather than repeating the commit.

This preview requires an existing HEAD and a registered repository root with a local `.git` directory. Unborn repositories, linked worktrees, in-progress merges/rebases/cherry-picks, hooks, signing, content filters/LFS, and remote operations are outside the supported slice. Files are staged as raw UTF-8 bytes; no attributes-based transformations or external programs run. External filesystem writers are not an OS-level transaction; avoid concurrent repository writes during execution. Korean approval framing is included; model-facing tool descriptions and activity remain English.

Next: credential-safe remote inspection, then fetch and push with explicit destination/branch/commit previews and transport qualification. Branch switching, merge/rebase, signing, submodules, worktrees, and LFS need separate design and compatibility checks. Current evidence is offline temporary-repository tests, mocked coding-loop approvals, and offscreen Qt checks; live-model Git execution and native visual review remain unverified.


## Local models and request timeouts

In the Code pane, open **Limits…** and adjust **Model call timeout (seconds)** for slow local models. The default is 300 seconds (five minutes), configurable from 10 to 3,600 seconds, for each Heavy or Light request. This bounds the complete request, including waiting for the first token and generation; it is not a streaming inactivity timer. **Total run time (seconds)** is a separate shared deadline and can end a model request sooner. New runs default to 900 seconds overall. Existing saved total limits are preserved; increase that limit too if needed. Older saved limits without the new field inherit the 300-second model timeout. Changes apply to the next run, and cancellation still discards late responses without replaying a request. This setting does not lengthen web fetch/search, shell-command, or Decision-advice deadlines.


## Filtered page reads

Direct public page reads accept unverified TLS certificates and hostnames to support TLS-inspecting networks; intermediaries can impersonate sites or alter returned content. Provider API connections still verify TLS. If a direct read encounters a recognized network-filter page or an eligible TLS, connection, or HTTP failure, Code can use configured keyed Firecrawl, Exa, Parallel, or eligible direct-Ollama retrieval APIs. Firecrawl Keyless is not used for page-fetch fallback. This sends the page URL to that provider and may incur provider charges. Activity records the fallback and Sources retain provider provenance. It does not forward browser/proxy credentials. Strict public-only mode, private or policy-blocked destinations, generic site denials, and timeouts do not use this path. See SEARCH_PROVIDERS.md for scope and validation limits.


## Focused project tools and test reports

`glob_files(path, pattern)` finds project-relative file paths using slash-separated patterns such as `**/*.py`, `src/*.ts`, and `src/**/test_?.py`. `**` is a whole recursive path component; `*`, `?`, and character classes match within one component. The pattern is always relative to the project root, while `path` selects the directory to scan. Results contain at most 100 files and are marked incomplete when traversal, depth or output limits stop the scan. Hidden paths are considered except for the existing protected paths; links and excluded paths are not followed. Git ignore files are not applied.

`grep_files(path, query, pattern, case_sensitive)` searches single-line literal text in matching UTF-8 files, returning paths and numbered line excerpts. Use `true` or `false` for case sensitivity; `**/*` selects files throughout the project. It scans files up to 2 MB each, at most 4 MB total, 2,000 directory entries, and 12 directory levels; output is bounded to 100 matches and 16 KB. The result marks incomplete scans and clipped lines. Binary, unreadable, linked, protected and oversized files are skipped. `regex_search` takes the same arguments and uses regular expressions, with a 50 ms per-line match limit and two-second total regex search limit; timeouts produce explicitly incomplete results. Patterns are single-line and at most 256 UTF-8 bytes. The existing `search_file` and `search_project` remain available. Neither searching nor filename discovery grants permission to edit file contents.

Heavy can call `project_overview` to inspect a bounded inventory (500 entries and four directory levels), common manifest names, languages, dependency names, script/entry-point names, and test configuration. Metadata is read rather than executed; dependency URLs and script bodies are not included. Results flag incomplete traversal or metadata. This is an orientation aid, not a complete dependency graph or validated test configuration.

`read_file_range(path, start_line, end_line)` reads inclusive 1-based line numbers, expressed as decimal strings. Files may be up to 10 MB of UTF-8 text; each call returns at most 1,000 lines and 64 KB of source text, with line numbers, a content snapshot, total line count, and next-line information. An individual oversized line is rejected. Range reads do not authorize whole-file replacement; ordinary full `read_file` is limited to 128 KB.

`apply_patch(path, old_text, new_text)` applies one exact replacement. Old text must be nonempty, unique in the entire file, and contained in a currently read range (or a full file read). Both arguments are limited to 64 KB and the resulting file to 10 MB. Ambiguous matches and stale reads are rejected. The file hash is rechecked at application and surrounding content is preserved. Read the changed region again before another patch. New files and full replacements still use `write_file` and its existing limits.

`run_tests(path, command, format)` uses the shell executor and the same explicit approval, optional Decision advice, environment filtering, process cleanup, output budget and time bounds. The preview identifies a test run and its report format. It executes project code with your account permissions and is not sandboxed. Supported formats are `auto`, `unittest`, `pytest`, `jest`, and `vitest`; the model selects a command appropriate to your project. The result contains the exit code, bounded output, the last recognized summary's reported counts, and bounded failure excerpts. A zero exit code without a recognizable summary is not claimed to verify passing tests. Truncated output is flagged and may leave the outcome unknown. Counts are parsed from untrusted test output rather than independently verified, and multiple summaries are not aggregated. Long suites remain subject to the existing shell/tool deadline (normally at most 45 seconds), separate from the model-call timeout. Use a focused command for this first slice.

These tools have offline project/model fixtures, an approved native temporary unittest check on the Windows host, and offscreen Qt approval checks. No live coding-model compatibility is implied. File access remains subject to the established sensitive-path, traversal, link, and project-containment checks.


## Task plan and checklist

For multi-step tasks, Heavy can create or replace a checklist with `update_plan(explanation, steps)` and read it with `get_plan()`. The `steps` argument is a JSON array encoded as a string, with objects such as `{"step":"Inspect the project","status":"in_progress"}`. Supported statuses are `pending`, `in_progress`, `completed`, and `blocked`. Plans contain 1–20 steps, each a single line of at most 200 characters, and at most one step may be in progress. The explanation is limited to 1,000 characters. Plan calls use the normal tool-call/context budgets and require no approval because they change only task metadata.

The Code pane shows a compact **Task plan** button with completion counts when a plan exists. Click to expand a read-only checklist and explanation; it starts collapsed to preserve transcript space. Plans are isolated per pane and saved independently of the bounded activity transcript. Cancellation, failure, and reopening retain the last reported steps; reopening never restarts work. Starting a new real coding run clears the previous task's plan. The simulation does not create or replace a coding plan.

Progress is model-reported, not proof that a step succeeded. Agentnik does not automatically mark unfinished steps complete when a run ends. Plans do not change the normal file, command, test, or Git permissions: project file operations proceed under the coding-run rules, and commands, tests, and Git mutations still require approval. Heavy owns the checklist; Light receives only the delegated context Heavy provides and cannot directly update the plan. Invalid or stale-run updates do not replace the visible saved plan. The interface framing is translated in the Korean preview; user/model step text stays in its original language.


## Calculator and Data Analysis — local tools

Calculator and Data Analysis tools run locally without Python eval, shell execution, filesystem access, or network calls. Calculator supports numeric arithmetic, pi/e, and common math functions; floating-point results are approximate. Data Analysis accepts explicitly supplied CSV/JSON row objects and reports missing/nonnumeric counts, numeric min/max/sum/mean/median/sample standard deviation, and optional grouping. Bounds: 1,000 rows, 32 columns, 10 groups, a 16 KB data request and 24 KB output, further constrained by shared tool argument/context budgets (Chat defaults to a 4 KB argument budget). Group keys preserve typed JSON values; missing values are excluded from numeric statistics. No formulas, SQL, arbitrary Python, charts or implicit file reads run. Code Heavy has both tools without enabling research; Light has no tools. Chat requires the separate **Calculator / Data tools** opt-in and a tool-capable model. Web access stays independently controlled; enabling both uses the configured Agentnik-managed route and its capability/access checks. Inputs sent by the user are already shared with the selected model; results return to that endpoint and retained tool activity/history. Attached CSV/JSON text can supply data; automatic full-dataset attachment retrieval remains future work.


## Scoped AGENTS.md guidance

Code now loads the selected project root's `AGENTS.md` before the first Heavy request. Ancestor `AGENTS.md` files within that root are loaded lazily when a tool targets a file/directory, including explicit Git path lists. `get_project_instructions(path)` lets Heavy discover rules before planning a change. Files outside the selected root, unrelated subtrees, other instruction filenames and user-global instructions are not automatically read. An instruction file applies to its parent directory and descendants; deeper rules take precedence only within their subtree. Explicit user instructions and Agentnik's fixed permission/security rules retain priority. This is model guidance, not a guarantee that every generated change follows a convention.

Activity reports loaded/removed instruction paths and scopes without copying raw guidance into activity logs. Heavy receives the current scoped guidance with its protocol-specific instructions; Light receives the same loaded scope map as bounded task context while remaining tool-free. Configured credentials are redacted. Automatic guidance reads do not authorize editing those files; the existing read-before-edit rules still apply.

If a tool batch discovers new/changed guidance, inspection tools may continue, but mutations, shell/test commands and delegation are deferred until a subsequent model turn can consider the updated instructions. Loaded scopes are refreshed between rounds. Changes detected before a file operation or before/during an approval invalidate the operation; the model must reconsider and submit it again. File changes still undergo state checks, and shell commands and Git mutations require approval. Filesystem writers remain concurrent; these checks are not an OS-level transaction. Shell scope uses the supplied working directory; Agentnik does not parse commands to infer every affected path, so the model is instructed to inspect affected paths first.

Guidance must be regular, unlinked UTF-8 files: up to 8 KB per file, 24 KB total, 16 loaded files, 24 directory levels and 256 discovered scopes, plus the shared run context/time budgets. Missing files are allowed; unsafe, unreadable or oversized guidance fails closed rather than silently truncating rules. New runs reload current files; reopening a saved session does not execute or load guidance by itself. Offline tests cover scope discovery, refresh/removal, path/link/encoding/size rejection, first-request protocol injection, credential redaction, mutation deferral, stale approval invalidation, unchanged shell approval, Light context and run-budget enforcement. Live model instruction adherence remains unqualified.


## Repository Skills preview

Code can discover and explicitly select up to five repository skills under `.agents/skills/<name>/SKILL.md`. Preview the instructions in the picker; selection persists in the session. Each run loads selected instructions and records their SHA-256 in activity. Selected skills can supply bounded UTF-8 references through `read_skill_resource`; relative paths are confined to the skill directory and linked paths are rejected. Scripts still require normal shell approval. Discovery is limited to 200 entries and 50 valid skills; each instruction or reference is limited to 16 KB and shared context budgets apply. Skill frontmatter uses bounded safe YAML parsing. User-level libraries and a bounded per-run revision history are available; richer metadata remains future work.


User-level skills under `~/.agents/skills` are also available in the picker. Repository skills keep their existing names; user skills use `user:<name>` identifiers, so duplicate names never silently override one another. Selected user instructions and references retain the same read bounds and approval rules. The list is scrollable and displays each source. Additional per-run archival beyond the current bounded history remains future work.


Selected skill IDs, sources, and exact instruction-file SHA-256 hashes are retained as metadata for the latest real coding run. Starting another run replaces those records; reopening never executes skills. Skill frontmatter uses bounded safe YAML parsing.

The Skills picker previews a snapshot of each instruction file. If a selected skill changes while the picker is open, saving the selection is refused; reopen the picker to inspect and select the new revision. A selected skill that changes after saving also blocks the next run until the selection is confirmed again. Supporting resources are read separately when requested and are not pinned by the instruction-file hash. Once read, each resource is checked for changes or removal during that run; a change stops the run before further work. Resources are loaded afresh on later runs.


Code sessions retain skill revision metadata for the most recent 32 real coding runs. Each record identifies the run and selected skill sources and SHA-256 hashes; simulations do not add records. Older sessions remain readable. The hashes identify instruction-file contents without storing those contents in the revision history.


Use **Skill history…** in the Code pane to review the recorded skill IDs, sources, and SHA-256 hashes for the latest 32 real coding runs. A missing selected skill stays visible in the selector until you explicitly uncheck it; a run cannot load it until it is restored or deselected.


Selected skills can list supporting resources via `list_skill_resources`, bounded to 200 entries, 100 files, and four directory levels. Paths remain confined to the skill directory and linked paths are excluded. Listing does not read or execute scripts.


## Skills updates and parallel Light analysis

Selected skill instruction hashes are pinned for the duration of each coding run. If an instruction file changes or becomes unavailable, Agentnik stops the run, invalidates any pending operation and asks the user to review before restarting. Newly confirmed selections also retain their instruction hashes between runs. If a selected instruction file changes or disappears, open Skills, review it and confirm the selection again, or deselect it. Older sessions without saved selection hashes remain compatible and acquire them when the selection is confirmed. Skill instructions and scoped repository guidance are included in Light analysis context under the shared context budget.

The first subagent slice adds `delegate_parallel`: with Allow Light model delegation enabled, Heavy can request two or three independent, concurrent analysis tasks using the configured Light connection or either of two optional alternate subagent connections and models. Children have no tools, filesystem access, web research tools, nested delegation or independent approvals; they receive the supplied task context, selected skills and scoped guidance. Heavy may request up to three project-file snapshots per task, limited to 8 KB each; every transfer requires individual approval of the displayed file text, task, model and endpoint, and changed files stop the batch. Requests, elapsed time and continuation context share parent limits. Activity identifies each task, model, completion/failure, elapsed time, provider-reported input/output tokens and bounded findings as each child finishes. Missing token counts remain unknown; returned results remain in original task order. Partial failure is returned to Heavy without automatic replay; cancellation discards late results. Later F4 work includes controlled self-service read-only project and optional web tools, more configurable model roles, and richer per-child usage reporting.


The two optional alternate subagent models in the collapsed Models panel let Heavy select `light`, `alternate`, or `alternate2` for each parallel task; omitted roles use Light. Both require Allow Light model delegation and a configured Light model. Each task, selected Skills, scoped guidance and approved file snapshots go to the chosen endpoint. Each file-transfer approval names that task’s exact model and endpoint; configured credentials are redacted. An unavailable or unconfigured role fails without model fallback. Each alternate assignment is saved as a connection name and model alias, never its credentials.


The Code pane shows a collapsible Subagents view with the latest status and bounded findings for up to 32 children in the current real coding run. Select an active child and choose **Cancel subagent** to stop waiting for that child while its siblings continue. Heavy receives a cancelled result without the child’s late output. An identical task and file scope cannot be retried or reassigned during the same run; changed wording still depends on model compliance. Cancelled and interrupted children remain visible; reopening never resumes work. Starting a new real run clears the prior view, while simulation preserves it. Cancellation stops waiting and scheduling; a request already submitted to a model endpoint may continue remotely.

### Independent document review

With Light delegation enabled, ask Heavy to review a project document independently. Choose a comprehension, requirements, design, or implementation-readiness review. Heavy can propose one UTF-8 document up to 8 KB and a configured Light or alternate model for each pass. Requirements, design and readiness passes can also propose one to three distinct project evidence files, each at most 8 KB. The approval shows the fixed role, exact instructions, document and evidence, endpoint, model, document and evidence SHA-256 hashes, and transmitted-input hash. Approve the entire displayed input, or reject to skip. Configured credentials are redacted from document and evidence text; original and redacted evidence hashes are shown. Each reviewer receives no drafting conversation, prior findings, selected Skills, scoped guidance, unapproved files or tools. The selected endpoint receives the displayed content; it may retain its own server-side context.

Each reviewer returns bounded, attributed, untrusted findings, elapsed time and available usage. Requests run sequentially, each with its own approval and shared run budgets; no multi-review batch is available yet. The Subagents view supports cancellation, and a cancelled review of the same file cannot be retried in that run. Agentnik discards findings if the document or any evidence changes before or during review; it does not monitor later changes or preserve a durable reviewed approval. Reviews do not authorize implementing suggestions.
