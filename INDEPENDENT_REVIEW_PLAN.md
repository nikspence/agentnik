# Independent document review implementation plan

Status: **independent review, project-local snapshot, and bounded read-only drift previews are implemented.** This plan elaborates the F4/F5 roadmap in [AGENTNIK_PLAN.md](AGENTNIK_PLAN.md). Current review tools and limits are described in [Coding features](CODE_FEATURES.md). This document is a design and delivery plan, not evidence of live model compatibility.

## Goal and existing baseline

Give a user an optional, inspectable review of a project document, including a selected track specification, before deciding what to change or implement. Independent reviewers examine approved snapshots with fixed rubrics and no drafting history. Their findings are attributed suggestions; neither a successful request nor agreement among models proves correctness.

Today Heavy can request sequential comprehension, requirements, design, or readiness reviews, including a structured response, or request a parallel batch through `review_document_parallel`. Users can also directly configure independent passes, including a bounded drift comparison. Each request needs approval of its full payload and destination; it receives no drafting conversation, prior findings, selected Skills, repository guidance, or tools. Document and evidence hashes are checked before and after the request; changed inputs discard findings. Activity/subagent records are bounded display summaries; structured results can be explicitly saved in session or project-track snapshots. `delegate_parallel` is a different feature: it includes Heavy-supplied tasks, Skills and guidance, so it must not be presented as independent review.

Track v1 keeps `track.json`, `spec.md`, and `plan.md` in the project. `prepare_track` computes a digest from those files and optional project context; selected-track progress is separate, session-local, model-reported data. Do not change the v1 metadata contract or treat its task evidence as review findings. Older sessions and projects without tracks must continue to work.

## User workflow

1. The user explicitly opens independent review for a project document or selected track. For a track, default the target to its `spec.md`; show the exact path and track identity. Opening the view makes no model call and grants no permission.
2. The user chooses review passes, configured Light/alternate roles, and project evidence for each eligible pass. Offer a small preset and individual controls; comprehension is document-only, and requirements, design, repository fit, and readiness can be selected independently. Repository fit requires explicit evidence. Show that a selected role may point to the same provider/model as another and that provider-side isolation cannot be guaranteed. Do not assume a model supports a protocol or capability from its listing.
3. Preview each request's fixed instructions, complete redacted target and evidence, original and transmitted hashes, model, endpoint, and estimated input size. Identify excluded material, untrusted content, unavailable or truncated evidence, and possible provider costs. Reject oversized sources rather than silently truncating the approved snapshot. No implicit web access, links, Skills, project guidance, or previous findings enter the payload. Network evidence, if ever supported, needs a separate permission and provenance design.
4. The user approves each exact destination and payload or skips/rejects it. An approval applies only to that payload, role, destination and revision, and cannot be reused for another reviewer. A batch may start approved requests together only after all selected previews have been handled and inputs rechecked. A rejected pass is shown as skipped; rejection never triggers a substitute model or less isolated request.
5. Show each pass as queued, running, completed, failed, cancelled, skipped, interrupted, or stale. Display model, elapsed time, reported usage or unknown, snapshot hashes, bounded findings and any truncation. Allow cancellation of a pass or batch. A remote request may continue after local cancellation; late results are discarded and uncertain work is not replayed. Preserve independent findings and disagreements; never invent consensus.
6. The user can mark each finding accepted, contested, deferred, or unresolved, with an optional bounded rationale. These are user decisions, not instructions to run tools or change files. The user chooses whether to save review history with a track. The implementation-run preview shows the exact reviewed revision, all pass statuses, unresolved findings and dispositions. It offers explicit continuation even if review was skipped or incomplete, but never labels that state as passed. Existing track and operation approvals remain in force.

## Snapshot and request contract

- Use project-root path validation and regular, unlinked UTF-8 reads. Start with the existing 8 KB target and per-evidence limit and up to three distinct evidence files per pass; state any lower aggregate/context limit. Avoid symlink, junction, hard-link, traversal and protected-path escapes through the existing `ProjectFiles` checks. Do not grant read-before-edit authorization from review reads.
- Capture source bytes and SHA-256 for each file; record the redacted transmitted content's hash separately, plus a hash of the complete exact reviewer input and a rubric version. Display the same snapshot that is sent. Configured credential redaction is not a guarantee that arbitrary secrets are detected; let the user inspect and reject the payload.
- Validate configuration, all pass definitions, destinations, file identities, limits and approvals before scheduling. Re-read sources after approval, immediately before each submission, and after completion; if any source changes or is unavailable, mark the affected results stale and discard their findings. Recheck again when displaying a saved result and immediately before an implementation approval. An external writer can race these checks; describe them as conflict detection, not a filesystem transaction.
- A reviewer request is built from scratch with the fixed, versioned safety policy and selected rubric, target, and explicitly selected evidence only. No tool definitions, prior assistant messages, drafting conversation, Heavy-supplied free-form instructions, Skills, guidance, search or implicit context. Protocol serializers must preserve that boundary for native Ollama, Responses, Chat Completions and Messages. Do not retry with a different model, context, tools, or provider on unsupported requests or uncertain failures.
- One pass produces bounded structured findings with stable local IDs, severity, concise title, rationale, optional target/evidence location, assumptions and suggested verification. Treat all fields as untrusted text. Validate schema and bounds; retain an explicit invalid/truncated response state instead of fabricating parsed findings or silently treating it as a clean review. Locations are reviewer claims, not verified anchors. Design the fixed output contract and bounded fallback for weaker models before implementation.

## Scheduling, budgets and failure behavior

Independent passes with already approved, self-contained inputs can run concurrently; a pass that requires another pass's output is a separate explicit later stage and must not be called fresh independent review. Initially cap a batch at three simultaneous reviewers, matching existing configured roles, with explicit per-provider constraints where known. Repeated roles/models are allowed when the user selects them; they remain separate requests and approvals.

Reserve shared request and input-context budgets for the whole batch before launching any child, and charge actual tool calls and returned content against the parent limits. Direct-review retained output is charged as UTF-8 bytes on completion; an output that does not fit is discarded and its pass fails. Heavy-requested batches charge their complete serialized tool result before continuation, without separately charging the same output. Use the existing parent deadline, model timeout, cancellation and process-wide worker bounds; enforce a per-pass output bound and the retained-record budget. If reservation fails, start none. Scheduling must check cancellation and current snapshots before every submission. Record failed or unstarted passes individually; one failure must not cause a sibling to be retried, discarded, or silently reassigned. Charge submitted attempts even if they fail or report no usage; report unknown token counts rather than estimating them as measured usage. Ensure the parent can continue with partial results within its remaining budget.

## Persistence and revision lifecycle

Use a versioned, validated review record separate from track v1's strict `track.json`; decide the final storage location in the first implementation slice after testing existing project/session and backup behavior. The intended durable option is an explicitly user-saved, project-local sidecar under the selected track, with bounded versioned JSON and normal per-file preview, approval, protected-path and conflict checks. No silent project write, network submission, staging or commit. Session-local drafts may support interruption recovery but must be clearly distinguished from saved project history. An ordinary untracked document can use session-local results without creating project files.

The minimum logical record contains a review ID and schema version; project/track identity; target and evidence paths, original and transmitted hashes; track digest where applicable; fixed rubric/version and exact input hash; role, sanitized endpoint identity and model; per-pass state, timestamps/duration, usage and bounded output; finding IDs, fields and user dispositions; and explicit truncation, error, stale and provenance indicators. Never store API keys or raw credentials. Preserve prior records when a new review is made; do not silently overwrite earlier dispositions. Avoid saving full source snapshots by default: hashes and bounded findings identify what was reviewed, while the approved preview is visible at submission. If retention of exact payloads is later offered, make it explicit, credential-safe and bounded.

Model output, project sidecars and imported records are untrusted. Validate types, sizes, IDs, status transitions and paths; a malformed or future-version sidecar stays untouched and is shown as unavailable/read-only. Define record and history caps and explicit export/delete behavior before shipping; never silently drop old results to make room. Use atomic single-file replacement with a base-hash recheck and clear conflict reporting. Concurrent writers can still race; retain earlier approved writes if a multi-file workflow stops.

Changing any target or selected evidence, missing/unreadable input, or a changed relevant track digest makes the applicable review stale. Preserve the earlier result and dispositions as historical, but do not apply them to the new revision. Track changes unrelated to a specific source should still invalidate a track-bound implementation approval because `prepare_track` binds the whole track and context. Editing a disposition is not approval of implementation. Reopening an interrupted session or saved review must never submit a request or resume a child. A failed, cancelled, skipped or interrupted pass must remain visibly distinct from a completed pass with no findings.

## Delivery slices

1. **Contracts and fixtures:** extract the current sequential request construction and snapshot checks into a reusable review component without changing behavior. Define rubric versions, pass/status/result schema, limits, endpoint display and credential handling. Add synthetic fixtures and tests for old sessions and v1 tracks. Keep existing Heavy tools compatible.
2. **Explicit batch preview and parallel execution:** add pass/model/evidence selection and full individual approval; implement bounded, fresh, tool-free concurrent requests and partial failure/cancellation reporting. Begin with session-local results. Verify each protocol payload and approval binding; do not claim durable review or implementation gating yet.
3. **Structured findings and track persistence:** parse bounded results, allow per-finding dispositions, and add opt-in project sidecar save/reopen with conflict checks, limits, validation, provenance and stale detection. Provide the review history and clearly separate it from model-reported track progress. Existing projects and sessions require no migration.
4. **Revision-bound implementation review:** integrate status, findings and dispositions into the selected-track start preview. Recompute track and source hashes at approval and before starting. Explicit continuation for unreviewed, incomplete, or stale reviews must show that state; it grants no later file, shell, Git or network permissions.
5. **Read-only drift reports:** separately compare an explicitly chosen approved specification revision with selected bounded current project snapshots. Show both revisions, evidence gaps and uncertainty, support cancellation and staleness, and never automatically rewrite a specification or project. Reuse approval and path controls; do not conflate drift findings with completion or independent implementation verification.
6. **Qualification:** complete provider- and platform-specific checks only when explicitly authorized and available. Record actual protocols, model versions, constraints and observed behavior; offline mocks establish contracts, not review quality, provider-side isolation, cost or real endpoint support.

Slice 1 progress: sequential review snapshot preparation, payload hashing and source rechecking now use a shared component. A reusable fresh-request builder verifies the approved input hash, length, model and endpoint before constructing a tool-free request; Responses requests include `store: false`. This requests provider behavior but does not prove provider-side isolation or retention. Sequential tool results identify rubric version 1 and in-memory result version 1 and are validated for bounded fields; their analysis remains unstructured, untrusted text. Exact version 1 rubric instruction hashes are pinned in offline tests. The approval and reviewer execution path remains in the coding loop. Offline snapshot, protocol request construction, sequential-review and selected-track tests cover this work; the durable history and structured finding formats and remaining slice 1 decisions are still outstanding.

Slice 2 preview: Heavy can request two or three independent passes through `review_document_parallel`. Each full input and destination is individually approved before any batch request; rejecting one stops the batch. Preflight rechecks the snapshots and reserves parent request and input-context budgets. The scheduler checks sources before and after requests, supports individual cancellation and partial failure, bounds output, and uses the existing model adapters. Requests to the same scheme/host/port are serialized; after a failed or cancelled pass, later passes to that endpoint are skipped because remote work may still be running. Results and Subagents status appear as passes finish, with provider-reported input/output tokens where available and unknown for missing or failed-request usage. Mocked tests cover request isolation, per-pass approval, rejection, concurrency, failure, stale inputs, cancellation and completion ordering. Additional lifecycle and compatibility qualification remains outstanding.

Users can also start **Independent review…** directly from Code with Light delegation enabled, selecting one to three roles and configured reviewer models and a project-relative document. Each non-comprehension pass has its own list of up to three evidence files; evidence is required for repository fit and drift, while comprehension is document-only. The same full-input approvals, bounded scheduler, cancellation and findings view apply; no Heavy request or drafting conversation is sent. A selected track's starting revision is retained as run context, not automatically sent as review evidence. Direct reviews preserve the coding draft, prior coding context and task plan. Offline mocked and offscreen tests cover selection, per-pass evidence isolation, approval/rejection and cancellation. Live model and platform qualification remain outstanding.

Direct-review adapter mocks also exercise fresh approved request bodies for Chat Completions, Messages, Responses and native Ollama, including credential and unselected-file exclusion, Responses `store: false`, and failure without retry when a reviewer requests unavailable tools. These checks do not establish actual provider support or provider-side isolation.

Completed direct and Heavy-requested parallel passes include validated elapsed time and provider-reported token counts in their findings records. These optional measurements persist with session snapshots and explicitly saved project history; missing token counts remain unknown, and legacy records without measurements remain readable. Failed and interrupted passes do not carry completed-pass measurements.

Non-completed parallel passes now retain bounded reasons for request failure, source changes, cancellation, same-endpoint skips and output-budget rejection in findings and saved records. Request failures use a generic explanation rather than preserving arbitrary provider error text. Legacy snapshots without reasons remain valid; interrupted passes without a received terminal event may not have one.

New direct and Heavy-requested parallel review records and progress manifests record the fixed rubric version, including interrupted and non-completed passes. Version 1 instruction hashes are pinned in offline tests, including the structured response contract, drift and repository-fit instructions. Older records remain readable with their version unspecified; unsupported future versions are not silently interpreted.

New parallel review records and progress manifests also include the connection protocol and a sanitized origin (scheme, host and port). Paths and credentials are not retained; a host containing a known configured secret is omitted. Distinct paths or accounts on the same origin remain indistinguishable, and arbitrary secrets in hostnames cannot be identified reliably. Older records need no migration.

Offline simulated transport now exercises the real adapters for all four routes with non-streaming completed and incomplete replies and successful streaming replies. Incomplete replies fail the pass without retaining findings or replaying the request. This does not test a real endpoint or establish review quality.

The direct-review dialog offers an explicit opt-in to save pass progress in the coding session. Once all inputs are approved, the full pass manifest is saved with interrupted placeholders and acknowledged before any reviewer request can start. Each received terminal result updates that snapshot; if the initial save fails no request starts, and if a later save fails the run stops with the last saved state retained. Reopening never resumes requests. This saves pass progress, not later disposition edits or project-sidecar history; those still require explicit saving. It is subject to the existing ten-snapshot and 256 KB session limits. Offline tests cover the pre-request save boundary, failure, cancellation and reopen, not a physical crash or cross-platform durability.

The Code pane's separate **Save Heavy review progress** opt-in applies this manifest-before-request boundary to Heavy-requested parallel independent-review batches. Every approved batch gets its own session snapshot; a manifest save failure prevents that batch's reviewer requests, and a later progress-update failure stops the coding run. The setting is off by default and persists per coding session. Single sequential review tools and ordinary subagent delegation are not included. Offline mocked and offscreen tests cover approval, manifest acknowledgment, progress updates and reopen; physical crash and live-model qualification remain outstanding.

Forced-stop evidence: an offline offscreen Windows test forcibly terminated its own direct-review and Heavy-requested review subprocesses after each reached a blocked mocked reviewer request. Reopening the temporary SQLite sessions retained all approved passes as interrupted and did not submit a model request. This checks one process-stop point per route, not power loss, every crash point, live provider behavior, or other operating systems.

The direct dialog also offers a **Specification / evidence drift** pass. It requires one to three explicit project evidence files and compares only their bounded snapshots with the selected document, using the same full-input approval, source rechecks, cancellation and untrusted structured-finding workflow. No files, tests, commands or network research are invoked automatically. An empty result is not proof of consistency; evidence gaps and model uncertainty remain material. Offline mocks cover approval, evidence inclusion, read-only behavior and result validation. This is not a full repository audit or live-qualified drift detector.

The direct dialog also provides a **Repository fit** pass with one to three explicit project evidence files. Its fixed rubric examines the proposal against only those snapshots, including interfaces, conventions, dependencies and integration risks; it does not establish repository-wide compatibility. It uses the same approval, freshness and structured-result boundaries. Offline mocked and offscreen tests cover payload isolation, required evidence and saved-result validation; live model quality remains unqualified.

The Subagents panel includes a **Review findings…** view of recorded pass statuses, validated structured outputs, review source and payload hashes for the current parallel run. Opening it checks current target and evidence hashes and labels changed or unavailable sources stale; this is a point-in-time check, not continuous monitoring or a filesystem transaction. Individual findings can be marked unresolved, accepted, contested, or deferred with an optional rationale. Current findings and dispositions clear with the pane or next run; after a run the user can explicitly save recorded statuses and dispositions as an immutable coding-session snapshot, viewable after reopening with another source check. A saved finding disposition can be revised by explicitly creating a new snapshot; the original stays intact and the new record retains its reviewed source hashes. Completed, failed, cancelled, stale and skipped pass records are retained when received. Approved passes registered in the pane without a terminal event become interrupted when the run stops. Without the applicable progress-saving opt-in, passes rejected before registration or events not received before the pane closes cannot be reconstructed; older snapshots contain completed passes only. Snapshots are limited to ten and 256 KB per session. The user can delete individual session snapshots after confirmation; a failed storage write leaves the in-memory and saved history intact. They are separate from project-track history and implementation approval. Invalid and truncated output states remain visible without fabricated findings. Physical crash testing remains future work.

For reviews in a selected-track run, each pass records the track ID and the digest of the track and project context selected at the start of the run. Current and saved findings views recompute that digest and report a changed or unavailable context separately from document/evidence staleness. This is an association with the run context, not evidence that the reviewer received the full track; only its approved document and evidence were sent. Earlier session snapshots without this metadata remain readable. It does not yet bind an implementation approval or create project-local track history.

Project-local history: `agentnik/track_review_storage.py` defines a version 1 `agentnik-plans/tracks/<track-id>/reviews.json` sidecar containing up to ten validated session snapshots associated with that track. In **Saved review snapshots…**, a user can explicitly select a track-associated snapshot, inspect the complete diff and approve appending it. The UI rejects known configured connection and search credentials, but arbitrary secrets cannot be identified reliably; inspect the diff. It rejects incompatible or duplicate records and checks track and sidecar state before applying through the existing file-edit boundary. A changed file or track stops the write; no model, shell, Git or network call occurs. A user can read project-sidecar history from **Spec & Plan** in another session, with point-in-time source and track checks. Offline temporary-project and offscreen tests cover creation, rejection, append, foreign tracks, credentials, approval-time conflicts and cross-session viewing. Full cross-platform validation remains outstanding.

The project-history view can also remove an individually selected snapshot after full-diff approval. It preserves session snapshots and other project records, and leaves an empty valid sidecar when the final entry is removed. The same track and sidecar conflict checks apply; rejection or a concurrent change does not apply the proposed removal.

The selected-track start preview shows matching session and project snapshots, labeled by origin, with their pass states, source and track revision status, findings and user dispositions, including unresolved defaults. It identifies missing older or unsaved reviews and does not silently deduplicate the same snapshot across origins. Continuing requires the existing explicit run confirmation; changes to the displayed records or their source status during the preview stop the start, and the existing track revision recheck still applies. The background run rechecks project history and approved source statuses before its first model request; an invalid or changed sidecar or a change from matching to stale stops the run. This is not continuous monitoring, an atomic filesystem transaction, or detection of every change to an already-stale source. The preview does not send saved review findings to the model or grant later operation permissions, and is not proof that every pass ran.

The structured response parser is used by the opt-in sequential `review_document_structured` tool; Heavy can request it with one to three evidence files, subject to the same complete-input and destination approval. The activity shows parse status and bounded raw output, and the structured findings go to Heavy; there is not yet a dedicated findings UI or durable history. Version 1 accepts only a JSON object with `version: 1` and `findings`: up to ten objects with exactly `severity` (`high`, `medium`, `low`, or `unknown`), `title`, `rationale`, `location`, `assumptions`, and `verification`. Title and rationale must be nonempty; the other text fields may be empty. The parser limit is 16,000 UTF-8 bytes, with individual limits of 160/2,000/500/1,000/1,000 characters respectively; the current sequential review's 8,000-character output cap can mark a longer response truncated first. Agentnik assigns local IDs in order. Duplicate JSON keys, unknown fields, malformed or partially invalid data produce an `invalid` state with no findings; an oversized or explicitly truncated response also yields no findings and its own status. An empty findings array is a valid response, not a verified clean result. Dedicated safe display, parallel execution, durable dispositions and live model qualification remain outstanding. Existing free-text sequential tools are unchanged.

## Acceptance and validation

- Offline unit tests cover schema and bounds, multiple roles including the same model, exact approval/payload hashes, redaction, invalid records, legacy sessions, sidecar conflicts and stale snapshots. Mock each supported protocol and prove no conversation, Skills, guidance, prior findings or tool definitions leak into reviewer input.
- Deterministic concurrency tests cover three independent passes, shared budget reservation, provider limits, out-of-order completion, one-pass failure, individual and batch cancellation, late results, changed files before/during/after requests, and no replay or fallback. Check reported usage, missing usage and charges for submitted failed attempts.
- Offscreen Qt tests cover selection, exact previews, per-pass approval/rejection, keyboard/accessibility, light/dark display, status and disagreement, dispositions, reopen without execution, stale/unavailable records and revision-bound track continuation. Test multiple tabs and prior drafts independently.
- Tests use temporary projects and application data; no paid or live requests in ordinary validation. Separately document authorized live model/protocol checks, native platform review and any gaps. A check of request construction alone is not a claim of reviewer quality or provider isolation.

## Decisions to resolve during slice 1

- Final sidecar name, schema, history size/retention and explicit deletion UX, with particular attention to user-controlled version control and concurrent edits.
- Exact structured response format and handling of partially valid, oversized or truncated model output, including a usable small-model preset.
- Provider concurrency limits and budget accounting when several configured roles share one endpoint or credential, without storing credentials in review records.
- Whether a separate user-initiated review dialog and Heavy-requested tool share the same scheduler, and how the user chooses passes without allowing Heavy to override approval or freshness boundaries.
- How the implementation preview selects a relevant saved review when several histories exist, and how it makes missing evidence and unresolved or contested findings visible without declaring an automatic pass.
